# ADR 0001: Минимизация персональных данных

Статус: принято
Дата: 2026-09-30

## Контекст

Сервис бронирования обрабатывает имя пассажира, даты поездки, маршрут и
историю переходов. Часть этих данных — персональные. Правила проекта требуют,
чтобы персональные данные не попадали в обычные логи, не утекали в ошибки API
и не хранились шире необходимого.

## Решение

1. **Имя пассажира — минимально необходимое.** В домене это `Passenger.FullName`.
   Документы, удостоверяющие личность, не собираются: на этапе поиска они не
   нужны, и их не может вывести модель.

2. **Имя не выводится наружу.** Ответ API по бронированию возвращает
   `passengers: {"count": N}`, а не список имён. Клиент, которому имена нужны,
   уже отправил их сам. Проверка на утечку есть в `TestBookingResponseOmitsPassengerNames`.

3. **Имя хранится в отдельной таблице** `booking_passengers`, а не в строке
   бронирования. Обычный путь чтения не касается имён, а удаление бронирования
   удаляет их каскадно.

4. **Свободный текст пользователя** (`raw_query`) хранится с ограниченным
   доступом, не возвращается в API и удаляется вместе с бронированием. В логи
   он не пишется.

5. **Логи редактируются на уровне обработчика.** `logging.Handler` проверяет
   каждый атрибут по имени ключа и маскирует значение, поэтому забывчивое
   место вызова не приводит к утечке.

6. **Ошибки не отражают вход.** Наружу отдаётся код (`invalid_request`) и
   короткая фраза. Сообщение об ошибке не содержит ни входных данных, ни
   стека, ни URL поставщика.

## Последствия

- Диагностика инцидента ограничена: по логу нельзя восстановить, что именно
  написал пользователь. Это сознательный размен в пользу приватности.
- Восстановление бага требует тестового или обезличенного окружения.
- Срок хранения имён должен быть определён политикой развёртывания; в коде
  заложена возможность каскадного удаления, но сама политика вынесена из
  репозитория.
