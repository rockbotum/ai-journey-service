# AI Journey Service

Сервис бронирования путешествий с явным процессом состояний бронирования и
безопасной границей между ИИ и финансовыми операциями.

## Что это за сервис

Пользователь описывает поездку. Сервис превращает это в структурированное
намерение, ищет варианты у поставщика, удерживает выбранный вариант, и только
после **явного** действия пользователя подтверждает бронирование.

Ключевое свойство: **ИИ никогда не подтверждает, не отменяет и не оплачивает
бронирование.** Финансовые операции доступны только через отдельные endpoints,
требуют явного флага согласия и заголовка `Idempotency-Key`.

## Процесс бронирования

```
intent ──search_requested──▶ searching ──search_succeeded──▶ offered
                                                                  │
                                              hold_requested ─────┘
                                                            ▼
                                                   holding ──▶ held
                                                                │
                                        confirm_requested ──────┘
                                                                ▼
                                                      confirming ──▶ confirmed
                                                                │        │
                                                                │        └──cancel──▶ cancelling ──▶ cancelled
                                                                │
                                                   hold_expired┘──▶ expired
```

О любой неуспешной операции бронирование переходит в `failed` с коротким
кодом причины. Полная таблица переходов — в `internal/booking/state.go`.

## Архитектура

Пакеты разделены по правилам, а не по технике:

| Пакет | Ответственность |
|---|---|
| `internal/booking` | Домен: состояния, переходы, инварианты, деньги. Не знает ни о БД, ни о HTTP. |
| `internal/ai` | Граница доверия к модели: строгая схема ответа, отказ неизвестных полей, ограничение размера. |
| `internal/provider` | Интеграция с поставщиком: таймаут, backoff, отсутствие слепого повтора финансовых вызовов. |
| `internal/store` | Контракт хранилища: идемпотентность и оптимистическая блокировка. |
| `internal/service` | Оркестрация процесса. Здесь же обеспечивается порядок «сначала свежая цена, потом подтверждение». |
| `internal/auth` | Доступ к API. |
| `internal/httpapi` | Транспорт: валидация, единые ошибки, лимиты, редактирование ответов. |
| `internal/config` | Загрузка конфигурации. Секреты не печатаются и не попадают в ошибки. |
| `internal/logging` | Маскирование чувствительных данных на уровне обработчика логов. |

Зависимости идут внутрь: `httpapi` → `service` → `booking`. Домен не зависит ни
от чего, поэтому его правила тестируются без инфраструктуры.

## Запуск

Нужен Go 1.27.

```bash
cp .env.example .env      # заполнить реальные значения
make run
```

Конфигурация читается только из переменных окружения. Обязательные значения:
`DB_DSN`, `AUTH_CREDENTIALS`, `SUPPLIER_BASE_URL`, `SUPPLIER_ID`,
`SUPPLIER_API_KEY`. Если что-то не задано, процесс падает на старте с
перечнем всех проблем сразу — полусобранный сервис не запускается.

Каждая переменная описана в `.env.example` вместе с назначением и значением по
умолчанию.

### Контейнер

Образ многостадийный: тулчейн остаётся в сборочном слое, в runtime попадает
только бинарь на базе distroless. Итоговый образ — около 17 МБ, пользователь
`nonroot`, shell и пакетный менеджер отсутствуют.

```bash
make docker-build
make docker-run        # требует заполненных переменных окружения
```

Сборка образа сама запускает `go vet` и весь набор тестов, поэтому падающий
тест останавливает сборку, а не попадает в реестр. Проверка состояния
выполняется бинарем в режиме `-health-check`: в distroless нет ни shell, ни
`curl`, поэтому проба вызывает реальный HTTP-эндпоинт — контейнер, который
слушает порт, но не способен обслужить запрос, будет помечен как unhealthy.

Полезные цели: `docker-shell` (интерактив в сборочном слое, где есть
инструменты), `docker-clean`.

Секреты в образ не попадают: `.dockerignore` исключает `.env` и всё
секретоподобное, а конфигурация передаётся только через окружение или
`-e`. Для воспроизводимых продакшен-сборок закрепите базовые образы по digest.

### Стек: API вместе с PostgreSQL

```bash
cp deployments/.env.example deployments/.env   # заполнить и не коммитить
make compose-up      # сборка и запуск, контейнеры остаются работать
make compose-ps      # состояние, включая health
make compose-logs    # логи приложения
make compose-down    # остановить, том с базой сохраняется
```

Compose читает `deployments/.env` сам. Две переменные с секретами обязательны,
и Compose откажется стартовать с указанием того, чего не хватает, — так сервис
не поднимается в рабочем, но нерабочем состоянии.

Три детали, на которые уходит время, если не знать про них заранее:

- **`.dockerignore` обязан лежать в корне репозитория**, а не рядом с
  `docker-compose.yml`. Контекст сборки — корень, где `go.mod` и исходники, и
  Docker читает ignore-файл из корня контекста. Копия в `deployments/`
  игнорируется молча, и `.env` уезжает в сборку. Проверяется это только
  пробой, а не чтением файла.
- **Имя compose-проекта задано явно.** По умолчанию оно берётся из имени
  каталога с compose-файлом, то есть generic-`deployments`, и любой стек в
  каталоге с таким же именем оказывается в том же пространстве — один `up`
  начинает пересоздавать чужие контейнеры. Оговорка: `container_name` задаёт
  глобальное имя, поэтому два стека не могут одновременно называть свой
  контейнер `postgres-dev`.
- **Миграции применяются только на пустом томе.** Они подключены в
  `/docker-entrypoint-initdb.d`, но официальный образ postgres выполняет их при
  первом старте. На уже инициализированной базе файлы игнорируются, и
  `schema_migrations` сама не обновляется — применяйте вручную. Раннера миграций
  в сервисе нет.

## API

Все маршруты `/v1/*` требуют `Authorization: Bearer <key>`. Исключение —
`GET /healthz`, доступный без учётных данных для проб оркестратора.

| Метод | Путь | Назначение |
|---|---|---|
| `POST` | `/v1/bookings` | Зафиксировать намерение. Контактов с поставщиком нет. |
| `GET` | `/v1/bookings/{id}` | Текущее состояние бронирования. |
| `POST` | `/v1/bookings/{id}/search` | Найти варианты. Только чтение, ничего не резервирует. |
| `POST` | `/v1/bookings/{id}/hold` | Временно удержать вариант. Обязательства нет. |
| `POST` | `/v1/bookings/{id}/confirm` | Подтвердить. Требует `confirmed: true` и ключ идемпотентности. |
| `POST` | `/v1/bookings/{id}/cancel` | Отменить. Также требует явного согласия. |

Ошибки возвращаются единообразно и не раскрывают внутренности:

```json
{"error":{"code":"price_changed","message":"The price changed. Review it and confirm again.","request_id":"…"}}
```

Клиент должен ориентироваться на `code`, а не на текст сообщения.

Каждый ответ о брони содержит блок оплаты, включая подтверждённые:

```json
{"id":"bk_…","state":"confirmed","confirmation":{…},
 "payment":{"status":"not_supported","supported":false}}
```

Подтверждение у поставщика не создаёт финансового обязательства: деньги
двигаются только на отдельном платёжном шаге, которого пока нет. Поле не
опускается намеренно — клиент должен отличать «оплата невозможна» от «оплата
произошла, а поле забыли». Обоснование — `docs/adr/0003-payment-gap.md`.

## Безопасность

- **Идемпотентность** обязательна для всех операций, меняющих состояние. Повтор
  с тем же запросом возвращает первый результат; повтор с другим запросом —
  `409`.
- **Оптимистическая блокировка**: переход возможен только при совпадении
  прочитанной версии строки.
- **Цена перепроверяется** непосредственно перед подтверждением. Изменение цены
  блокирует подтверждение и требует нового решения пользователя.
- **Истёкший hold** нельзя подтвердить.
- **Ключи API хэшируются** при старте и не остаются в памяти в открытом виде.
- **Пароль не пишется в лог** на уровне обработчика: маскирование происходит
  централизованно, а не в каждом месте вызова.
- **Имена пассажиров не выходят в API**: в ответе только их количество.
- **Тело запроса ограничено**, частота запросов ограничена, неизвестные поля
  JSON отклоняются.

Подробности и обоснования — в `docs/adr/`.

## Разработка

```bash
make check      # fmt-check, vet, build, test, cover, lint
make test-race  # с детектором гонок (нужен C-компилятор)
make cover      # покрытие с порогом
```

227 тестов, покрытие 75.1% при пороге 70% в CI. Линтер и детектор гонок
локально не запускаются, если `golangci-lint` и C-компилятор не установлены —
в CI они обязательны.

## Состояние проекта

Реализовано: домен и процесс, граница ИИ, интеграция с поставщиком, хранилище,
оркестрация, HTTP API, аутентификация, конфигурация, логирование с
маскированием, миграция PostgreSQL, ADR, CI.

Известные пробелы, зафиксированные в ADR:

- Платёжный провайдер не подключён. API сообщает об этом явно
  (`"payment": {"status": "not_supported", "supported": false}`) в каждом ответе,
  а не прячет: подтверждение у поставщика не равно оплате.
- Хранилище — в памяти процесса. Схема PostgreSQL готова
  (`migrations/0001_init.sql`), адаптер — нет. Пока адаптера нет, есть
  несоответствие, которое всплывёт при его написании: `bookings.id` объявлен как
  `uuid`, а генератор выдаёт `bk_<timestamp>_<hex>`, и такой идентификатор в
  колонку не пишется. Нужно либо `text`, либо UUID в генераторе.
- Аутентификация — сравнение хэшей ключей вместо внешнего IdP.
- Лимиты частоты запросов не общие между инстансами.
- Запрос намерения на естественном языке ещё не подключён к `/v1/bookings`:
  граница ИИ готова и покрыта тестами, но не вызывается из HTTP-обработчика.
