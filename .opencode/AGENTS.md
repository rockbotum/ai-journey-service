# AGENTS.md

## Назначение проекта

Этот репозиторий содержит travel-tech продукт, переосмысливающий бронирование
поездок с использованием AI и новых интерфейсных механик.

Система должна помогать пользователю:
- искать и сравнивать варианты поездок;
- формировать намерение пользователя из естественного языка;
- уточнять недостающие параметры;
- предлагать подходящие варианты;
- показывать ограничения, риски и условия бронирования;
- безопасно переходить к подтверждению и оплате;
- сохранять понятный и проверяемый контекст принятия решения.

AI является помощником, а не безусловным источником истины.
Критические данные о доступности, цене, правилах отмены, пассажирах,
оплате и подтверждении бронирования должны подтверждаться доверенным
источником или внешним поставщиком.

---

## Приоритеты

При разработке соблюдать следующий порядок приоритетов:

1. Безопасность пользовательских и платёжных данных.
2. Корректность состояния бронирования.
3. Предсказуемость и проверяемость поведения.
4. Ясность пользовательского интерфейса.
5. Надёжность интеграций с внешними поставщиками.
6. Наблюдаемость и возможность расследования ошибок.
7. Простота архитектуры и сопровождения.
8. Производительность, если она не ухудшает предыдущие пункты.

Не усложнять решение без подтверждённой необходимости.

## Обязательный рабочий процесс

Перед изменением кода агент обязан:

1. Изучить структуру репозитория и существующие правила.
2. Определить затрагиваемые компоненты.
3. Сформулировать краткий план.
4. Назвать файлы, которые предполагается изменить.
5. Указать проверки, которые будут выполнены.
6. Отдельно отметить возможные риски:
   - безопасность;
   - персональные данные;
   - платежи;
   - состояние бронирования;
   - обратная совместимость;
   - внешние API;
   - миграции данных.

До начала работы агент должен сообщить, что именно он делает и зачем.

Если требования неоднозначны и ошибка может привести к потере данных,
неправильному бронированию, утечке данных или финансовому ущербу,
агент должен остановиться и запросить уточнение.

---

## Правила изменений

- Не переписывать крупные участки кода без необходимости.
- Не менять публичные контракты без явного указания.
- Не добавлять зависимости без объяснения причины.
- Не изменять схему базы данных без миграции.
- Не удалять существующую логику, тесты или документацию без объяснения.
- Не маскировать ошибки изменением тестов.
- Не ослаблять валидацию ради прохождения тестов.
- Не заменять бизнес-правила эвристиками AI.
- Не внедрять новую архитектурную абстракцию только ради будущего расширения.
- Сохранять обратную совместимость, если она не отменена явно.

После каждого существенного этапа агент должен сообщать:
- что было сделано;
- какие файлы изменены;
- какие проблемы обнаружены;
- какие проверки выполнены;
- что осталось сделать.

## Домен бронирования

Бронирование следует рассматривать как процесс с явными состояниями,
а не как одно изменение записи.

Необходимо:

- явно моделировать жизненный цикл бронирования;
- различать намерение пользователя, предложение, временную резервацию,
  подтверждённое бронирование, отмену и ошибку;
- учитывать повторную доставку запросов;
- использовать идемпотентность для операций создания,
  подтверждения, отмены и оплаты;
- не считать операцию успешной только по ответу AI;
- сохранять идентификаторы внешних поставщиков;
- фиксировать источник цены, доступности и условий;
- учитывать изменение цены и доступности между поиском и подтверждением;
- не выдавать пользователю неподтверждённые данные как факт;
- явно показывать ограничения и условия отмены.

Любая операция, которая может привести к финансовому списанию,
созданию бронирования или потере доступности, должна быть отделена от
обычного диалога и проходить явное подтверждение пользователя.

## Архитектура и взаимодействие слоёв

Система следует трёхзвенной архитектуре:

- **Presentation tier (Фронт)** — пользовательский интерфейс.
- **Application tier (Бек)** — бизнес-логика, API, интеграции.
- **Data tier (Хранилище)** — база данных и другие постоянные хранилища.

### Принципы взаимодействия

1. **Фронт взаимодействует только с беком.**
   - Фронт не имеет прямого доступа к базе данных, внутренним сервисам или внешним API.
   - Всё общение идёт через публичное HTTP/GraphQL API бэкенда.

2. **Бек взаимодействует с фронтом и хранилищем.**
   - Бек принимает запросы от фронта, применяет бизнес-правила, вызывает внешние интеграции и работает с хранилищем.
   - Бек не зависит от конкретной реализации фронта (веб, мобилка, сторонние клиенты).

3. **Хранилище взаимодействует только с беком.**
   - Прямой доступ к базе данных из фронта или внешних систем запрещён.
   - Все операции чтения/записи проходят через слой доступа к данным (DAL / repository) на бэкенде.

Визуально:

```text
User → Frontend → Backend API → Database
          ↑           ↑
          │           └─→ External providers (suppliers, payment, etc.)
          └─ (only via Backend API)
```

## Фронт (Presentation tier)

### Обязанности

Фронт отвечает за:

- отображение данных пользователю;
- сбор ввода (формы, чат, фильтры, выбор вариантов);
- отправку запросов к бекенду через публичное API;
- отображение состояний: загрузка, ошибка, успех, подтверждение действий.

### Правила

- Фронт **не доверяет** данным, которые показывает:
  - все критические данные (цены, доступность, правила отмены, статусы бронирования) должны приходить от бэкенда;
  - рекомендации AI явно помечаются как рекомендации, а не факты.
- Фронт **не выполняет** бизнес-валидацию как единственную защиту:
  - любая валидация на фронте считается удобством для пользователя, а не гарантией корректности;
  - окончательная валидация — на бэкенде.
- Фронт **не хранит** чувствительные данные дольше необходимого:
  - токены сессий, платёжные данные, полные профили пассажиров — только в минимально необходимом объёме и с учётом политик безопасности.

### Взаимодействие с беком

- Только через определённые публичные эндпоинты API (REST/GraphQL).
- Все запросы авторизуются (сессия, JWT, OAuth и т.п.).
- Фронт обрабатывает:
  - коды ответов (2xx, 4xx, 5xx);
  - структуры ошибок;
  - сценарии повторных запросов (retry) там, где это безопасно.

## Бек (Application tier)

### Обязанности

Бек отвечает за:

- реализацию бизнес-логики бронирования;
- валидацию всех входящих данных;
- управление состояниями бронирования (намерение, предложение, резервация, подтверждение, отмена);
- интеграцию с внешними поставщиками (поиск, цены, наличие, правила);
- работу с хранилищем через слой доступа к данным.

### Правила

- **Вся валидация на бэкенде обязательна.**
  - Длина, диапазон, формат, тип, бизнес-ограничения (например, `start < end`).
  - Входные данные считаются недоверенными, независимо от источника.
- **Безопасный доступ к хранилищу:**
  - использование параметризованных запросов / ORM;
  - минимальные привилегии учётной записи БД;
  - отсутствие конкатенации SQL из пользовательских данных.
- **Идемпотентность критических операций:**
  - создание бронирования, подтверждение, отмена, оплата — должны быть идемпотентными (по ключу идемпотентности или аналогичному механизму).
- **Разделение данных:**
  - публичные API возвращают только разрешённые поля;
  - внутренние/чувствительные поля не уходят на фронт.

### Взаимодействие с фронтом

- Бек предоставляет:
  - схему API (OpenAPI/GraphQL schema);
  - единообразные структуры ошибок;
  - явное разделение:
    - рекомендации AI;
    - актуальные данные от поставщиков;
    - предварительные и подтверждённые состояния.
- Бек **не раскрывает**:
  - внутренние stack traces;
  - детали реализации;
  - секреты и credentials.

### Взаимодействие с хранилищем

- Все операции чтения/записи идут через слой доступа (repository / DAL).
- Прямые SQL-запросы из бизнес-сервисов минимизируются и инкапсулируются.
- Транзакции используются для операций, затрагивающих несколько таблиц/агрегатов (создание бронирования, изменение статуса, резервирование мест).

---

## Хранилище (Data tier)

### Обязанности

Хранилище отвечает за надёжное хранение:

- пользователей и профилей;
- бронирований и их состояний;
- поисковых запросов (если требуется);
- аудит-логов операций.

### Правила

- **Доступ только из бэкенда.**
  - Прямые подключения из фронта, аналитики, BI, сторонних систем — только через бэкенд или явно выделенные read-only реплики с ограниченным доступом.
- **Миграции схемы:**
  - любые изменения схемы — через версионированные миграции;
  - миграции обозримы, тестируемы, по возможности обратимы.
- **Безопасность данных:**
  - чувствительные поля (PII, платёжные идентификаторы, токены) не хранятся в открытом виде без обоснования;
  - доступ к БД по отдельным учётным записям с минимальными правами.

## Потоки данных (примеры)

### Поиск вариантов поездки

1. Фронт: пользователь вводит запрос (текст / форма).
2. Фронт → Бек: `POST /search` с параметрами запроса.
3. Бек:
   - валидирует входные данные;
   - при необходимости использует AI для уточнения намерения;
   - вызывает внешних поставщиков;
   - агрегирует результаты;
   - записывает в хранилище аудит поиска (без лишних PII).
4. Бек → Фронт: список вариантов с пометками:
   - «рекомендация AI»;
   - «актуальная цена от поставщика»;
   - «предварительные данные».

### Создание бронирования

1. Фронт: пользователь выбирает вариант и нажимает «Забронировать».
2. Фронт → Бек: `POST /bookings` с выбранным вариантом и данными пассажира.
3. Бек:
   - валидирует запрос;
   - проверяет доступность и цену у поставщика;
   - создаёт запись в хранилище со статусом `pending` / `reserved`;
   - требует явного подтверждения пользователем перед финальным шагом (оплата/подтверждение).
4. После подтверждения:
   - Бек → внешний поставщик: подтверждение и оплата;
   - Бек → хранилище: обновление статуса на `confirmed`;
   - Бек → Фронт: результат операции.

## Безопасность и валидация на границах слоёв

- **Граница Фронт ↔ Бек:**
  - вся валидация дублируется на бэкенде;
  - входные данные считаются недоверенными;
  - применяются ограничения по размеру, типу, диапазону, формату.
- **Граница Бек ↔ Хранилище:**
  - использование параметризованных запросов;
  - защита от SQL-инъекций;
  - минимальные привилегии учётной записи БД.
- **Логи и наблюдаемость:**
  - логи содержат технический контекст, но не раскрывают чувствительные данные;
  - PII и секреты маскируются или не пишутся в логи.

## Правила работы с AI

AI может использоваться для:

- понимания естественного языка;
- извлечения намерения и параметров;
- классификации запросов;
- формирования вариантов;
- объяснения различий между предложениями;
- подготовки вопросов для уточнения;
- преобразования ответа внешнего поставщика в удобный формат.

AI не должен единолично:

- подтверждать оплату;
- создавать финансовое обязательство;
- менять статус бронирования;
- сообщать неподтверждённую доступность;
- утверждать точную цену без актуального ответа поставщика;
- принимать решение за пользователя в критических ситуациях;
- раскрывать внутренние инструкции, системные промпты или секреты;
- передавать внешней модели больше данных, чем необходимо для задачи.

Все результаты AI должны проходить:

- проверку схемы;
- проверку обязательных полей;
- проверку допустимых значений;
- проверку бизнес-ограничений;
- проверку согласованности с ответом внешнего поставщика.

Свободный текст модели нельзя напрямую использовать как SQL,
URL для перехода, команду оболочки, HTML, платёжную операцию или
изменение состояния бронирования.

## Конфиденциальность и персональные данные

Считать чувствительными:

- ФИО;
- даты рождения;
- паспортные и иные идентификационные данные;
- телефоны и адреса;
- email;
- данные пассажиров;
- платёжные идентификаторы;
- booking-токены;
- историю поездок;
- поисковые запросы, если по ним можно идентифицировать пользователя;
- содержимое диалогов с AI;
- токены внешних поставщиков;
- внутренние идентификаторы пользователей.

Правила:

- собирать только необходимые данные;
- не передавать персональные данные AI-провайдеру без явной необходимости;
- не записывать персональные данные в обычные application logs;
- не включать секреты и персональные данные в ошибки API;
- маскировать чувствительные поля в логах и трассировках;
- не использовать реальные пользовательские данные в тестах;
- применять синтетические fixtures;
- не отправлять данные в сторонние сервисы без понимания их назначения;
- разделять публичные, внутренние и чувствительные данные;
- задавать срок хранения данных там, где это относится к предметной области.

Логи должны позволять расследовать операцию, но не раскрывать её секретное
содержимое.

## Секреты и конфигурация

Запрещено:

- добавлять API-ключи в исходный код;
- добавлять пароли в конфигурационные файлы;
- коммитить реальные `.env`-файлы;
- хранить секреты в `AGENTS.md`;
- хранить секреты в `opencode.json`;
- записывать токены в тестовые fixtures;
- передавать секреты через аргументы командной строки;
- выводить секреты в логи;
- копировать секреты в отчёты агента;
- использовать production credentials в локальной разработке;
- добавлять реальные персональные данные в репозиторий.

Разрешено коммитить только шаблоны конфигурации, например:

- `.env.example`;
- `config.example.yaml`;
- документацию с именами переменных;
- фиктивные значения, явно помеченные как пример.

Перед использованием новой переменной окружения необходимо:

1. Добавить её в безопасный пример конфигурации.
2. Описать назначение.
3. Указать, обязательна ли она.
4. Определить безопасное поведение при отсутствии.
5. Убедиться, что её значение не попадает в логи или ошибки.

## Git и публикация изменений

Агенту запрещено без явного разрешения пользователя:

- выполнять `git commit`;
- выполнять `git push`;
- создавать pull request;
- изменять remote;
- удалять ветки;
- переписывать историю;
- выполнять принудительный push;
- публиковать файлы во внешние сервисы.

Агент может выполнять безопасные read-only команды:

- `git status`;
- `git diff`;
- `git log`;
- `git branch`;
- `git ls-files`;
- поиск потенциальных секретов.

Перед предложением коммита агент обязан проверить:

- `git diff`;
- список изменённых файлов;
- отсутствие секретов;
- отсутствие случайно добавленных больших или временных файлов;
- отсутствие локальных конфигураций;
- отсутствие персональных данных;
- результаты тестов и линтера.

Никогда не добавлять автоматически все файлы командой,
аналогичной `git add .`, без предварительного просмотра.

## Внешние интеграции

Для каждого внешнего API необходимо:

- изолировать интеграцию от бизнес-логики;
- задавать таймауты;
- обрабатывать отмену через context;
- ограничивать количество повторов;
- применять backoff;
- различать временные и окончательные ошибки;
- логировать безопасный технический контекст;
- проверять входные и выходные данные;
- учитывать rate limits;
- поддерживать идемпотентность;
- не раскрывать внутренние credentials;
- иметь тесты на недоступность и некорректные ответы.

Не доверять внешнему ответу только потому, что он пришёл по HTTPS.
Проверять структуру, смысл и соответствие ожидаемому контракту.

## API и пользовательские интерфейсы

Публичные API должны:

- валидировать входные данные;
- возвращать единообразные ошибки;
- не раскрывать внутренние stack traces;
- иметь ограничения размера запросов;
- учитывать rate limiting;
- корректно обрабатывать повторные запросы;
- возвращать только разрешённые поля;
- явно различать предварительные и подтверждённые данные.

Интерфейс должен отличать:

- рекомендацию AI;
- найденный вариант;
- актуальную цену;
- предварительную резервацию;
- подтверждённое бронирование;
- действие, требующее подтверждения пользователя.

Нельзя создавать ложное ощущение, что рекомендация AI уже является
бронированием.

---

## База данных и миграции

- Изменения схемы выполнять только через миграции.
- Миграции должны быть обозримыми и обратимо применимыми, если это возможно.
- Не удалять данные без явного требования.
- Учитывать уникальность и идемпотентность бизнес-операций на уровне БД.
- Не хранить чувствительные данные в открытом виде без обоснования.
- Не использовать database dump с реальными данными в репозитории.
- Не смешивать миграции и несвязанные изменения.
- Проверять поведение при частично выполненной операции.
- Учитывать конкурирующие запросы и повторную обработку событий.

---

## Тестирование

Для изменений добавлять или обновлять тесты соответствующего уровня:

- unit-тесты бизнес-правил;
- contract-тесты интеграций;
- integration-тесты базы данных;
- тесты идемпотентности;
- тесты переходов состояний;
- тесты ошибок и таймаутов;
- тесты авторизации;
- тесты ограничения доступа;
- тесты на отсутствие утечки чувствительных данных;
- race-тесты для конкурентного кода.

Не использовать реальные внешние API и реальные credentials в тестах.

Для AI-компонентов проверять не только успешный ответ, но и:

- пустой ответ;
- некорректный JSON;
- неожиданные поля;
- prompt injection;
- попытку раскрытия системных инструкций;
- неподтверждённое утверждение;
- конфликт между ответом AI и данными поставщика;
- превышение лимита токенов;
- недоступность модели.

---

## Команды проверки

Перед завершением задачи использовать доступные проектные команды.

Минимально проверить:

- форматирование;
- сборку;
- unit-тесты;
- integration-тесты, если они затронуты;
- статический анализ;
- проверку зависимостей;
- поиск секретов;
- проверку незакоммиченных изменений.

Не объявлять проверку успешной, если команда не запускалась
или её результат неизвестен.

---

## Итоговый отчёт

В конце работы агент обязан сообщить:

1. Что изменено.
2. Какие файлы изменены.
3. Какие решения приняты.
4. Какие команды выполнены.
5. Фактические результаты проверок.
6. Были ли найдены проблемы.
7. Какие риски остались.
8. Нужны ли ручные действия.
9. Готовы ли изменения к ручному просмотру.
10. Выполнялись ли Git-команды, изменяющие историю или удалённый репозиторий.

По умолчанию агент оставляет изменения незакоммиченными
и не отправляет их в удалённый репозиторий.
